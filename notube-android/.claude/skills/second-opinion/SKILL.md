# 다른 AI 검토 (프리타임 스킬)

작성한 사람(지금의 Claude)과 **다른 모델**이, **대화 맥락 없이** 코드만 보고 검토하게 해서 같은 사람이 같은 실수를 못 보고 지나치는 걸 막는다.

## 절차

1. **검토 범위 정하기**: 보통 마지막 커밋 몇 개 (`git log --oneline`, `git diff <base>..HEAD`). 범위와 의도를 한두 줄로 적는다.
2. **독립 검토자 띄우기**: Agent 도구로 새 에이전트를 띄운다 (fork 아님 — 맥락을 물려받으면 독립성이 사라진다).
   - `model`은 지금 대화 모델과 **다른 모델**로 (예: 지금이 opus면 `sonnet`, 아니면 `opus`).
   - 프롬프트에 넣을 것: 저장소 경로, 검토 범위(커밋), 앱이 하는 일 한 단락, 이번 변경의 의도, 그리고 아래 "검토자에게 줄 지시".
   - 작성자의 설명이나 변명은 넣지 않는다 (검토자가 코드만 보고 판단하게).
3. **결과 확인**: 검토자가 낸 지적을 하나씩 직접 코드에서 확인한다. 맞는 지적만 고치고, 틀린 지적은 왜 틀렸는지 한 줄로 남긴다.
4. **고친 뒤**: 지적마다 회귀 테스트를 추가하고 전체 테스트·린트·빌드를 돌린다.
5. **사용자에게 보고**: 검토자 모델, 지적 수, 고친 것 / 고치지 않은 것(이유)을 짧게.

## 검토자에게 줄 지시 (그대로 붙여 넣기)

> 너는 이 저장소를 처음 보는 독립 코드 검토자다. 지정된 커밋 범위의 변경을 읽고, 실제로 잘못 동작하는 버그만 찾아라: 계산 오류, 경계 조건(자정·요일·시간대), 상태가 저장/복원될 때 깨지는 것, 동시성, 안드로이드 생명주기·권한, 그리고 사용자가 앱의 제한을 우회할 수 있는 허점. 스타일 지적은 빼라.
> 각 지적은 파일:줄, 한 문장 설명, 그리고 "이런 입력/상황에서 이렇게 잘못된다"는 구체적 시나리오를 함께 적어라. 확신이 없으면 '불확실'이라고 표시하라. 코드를 수정하지 말고, 필요하면 테스트(`./gradlew --no-daemon -Pkotlin.compiler.execution.strategy=in-process testDebugUnitTest`)를 돌려 확인만 해라. 마지막에 지적을 심각한 순서로 정리해라.
