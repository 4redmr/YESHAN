# 데이터 소스 설계 (확정, 2026-10-20)

[README.md](README.md)의 1단계 조사를 바탕으로 데이터 소스 역할을 확정한다.

## 소스별 역할

| 데이터 | 소스 | 비고 |
|---|---|---|
| 기본정보(이름/주소/좌표/카테고리/전화번호) | 카카오 로컬 API(키워드 장소검색) | 월 10만 건 무료. 평점/리뷰 필드는 없음 — 기본정보 전용. |
| 평점 + 리뷰 텍스트 | 구글 Places API (Text Search) | 평점만이 아니라 리뷰 텍스트도 가져온다(`places.reviews`). 캐싱 금지 정책이라 조회 시점마다 실시간 호출하고, DB엔 매칭용 place_id 외 장기 저장을 하지 않는다. |
| "앱 간 평점 괴리" | 보류 | 네이버·카카오가 평점을 API로 안 줘서 자동 비교가 불가능. 네이버가 평점을 공식으로 열어주면 재검토. |

## 왜 구글 단독으로 가는가

- 신뢰도 신호(평점·리뷰·광고 의심도)는 구글 Places 하나로 충분히 만들 수 있다.
- 카카오는 "이 가게가 어디 있고 뭘 하는 곳인지"만 담당하면 되고, 평점 비교 역할은 애초에 할 수 없다.
- 이렇게 역할을 나누면 카카오 쪽 약관(수집 목적 사용 금지)과 구글 쪽 약관(캐싱 금지) 둘 다 "필요한 시점에 1건씩 조회"하는 구조로 자연스럽게 지킬 수 있다.

## 리뷰 텍스트를 포함하기로 한 이유와 트레이드오프

- `ad-review-filter.md`의 광고 의심 점수(R1~R6)는 리뷰 "텍스트"가 있어야 계산할 수 있다. 평점 숫자만으로는 R1(명시적 키워드) 같은 핵심 신호를 아예 못 쓴다.
- 비용은 올라간다(Text Search 기준 Enterprise+Atmosphere $40/1000건, 평점만일 때 $35/1000건). 조회량이 적은 프로토타입 단계에서는 문제 없지만, 트래픽이 늘면 재검토 대상.
- Places API(New) Text Search는 가게당 최대 5개 리뷰만 준다. 광고 의심 판별에 5개면 충분히 시작할 수 있다는 가정으로 진행.

## 적용 범위 (이번 단계)

- `trust_score.py`: 평점/리뷰수 판정에 더해, `places.reviews` 텍스트를 받아 `ad_filter.py`의 규칙(R1~R3)으로 광고 의심 점수를 매긴다.
- `kakao_basic_info.py`: 카카오 로컬 API로 기본정보만 따로 조회하는 스크립트(평점과는 독립적으로 둠 — 역할 분리를 코드 구조에도 반영).
